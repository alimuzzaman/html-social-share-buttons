# Rewrite compatibility decisions

These decisions separate required 2.2.6 compatibility from deliberate defect
corrections. They apply to the first rewritten release unless a later approved
decision replaces them.

## Exact compatibility surfaces

- Frontend HTML, whitespace, attribute order, classes, legacy asset URLs,
  filter order, and supported public entrypoints remain byte-compatible.
- The `zm_shbt_fld` option name, submitted field shape, defaults, unknown
  extension keys, autoload behavior, and `_zm_sh_disable_share` post meta stay
  unchanged.
- Legacy constants, globals, functions, classes, interfaces, public methods,
  public properties, magic icon-set access, hooks, asset handles, builder IDs,
  and stored builder representations remain available through
  `Compatibility/Legacy`.
- Bluesky's historical `%0A` URL suffix, analytics inline-script behavior,
  X's `twitter` CSS/file naming, and the widget numeric-list rendering defect
  remain unchanged because changing them would alter frozen output or saved
  behavior.

## Intentional defect corrections pending release sign-off

- The implementation currently parses the complete URL-encoded AJAX settings
  body before applying the
  historical field sanitizer. The old order silently discarded fields after
  the first separator.
- AJAX handlers currently terminate through WordPress response APIs so test
  and runtime termination semantics are consistent while response bodies stay
  unchanged.
- The block currently declares editor dependencies generated by the WordPress
  build and loads only compiled bundles.
- WPBakery currently enqueues its bundle once, localizes its nonce once,
  accepts either a JSON string or an already-parsed response, and inserts
  server-provided labels as text rather than HTML.
- Malformed mixed-type builder attributes currently normalize to safe
  empty/default values. Valid persisted shortcode, block, Elementor, and
  WPBakery values retain exact output. These corrections require explicit
  product sign-off before the release candidate is published.

## Storage, migration, and rollback

- There is no custom table and no replacement option in this release.
- No migration step is registered, no schema-version option is written, and
  activation/deactivation/uninstall does not mutate settings.
- Canonical value objects normalize in memory only. Saving maps back to the
  historical shape.
- Rolling back to 2.2.6 reads the same option and post meta without a reverse
  migration.

## Assets and API lifetime

- Canonical icon assets live under `assets/iconsets/<set>/<shape>/<network>`.
  Compatibility continues to emit historical public URLs until provenance,
  browser parity, and an explicit URL-transition decision are complete.
- The working policy is to support the full legacy API throughout 3.x, without
  runtime deprecation notices in 3.0, and consider removal only in 4.0 after a
  documented deprecation period.
